## ЗАДАЧА W-1 · VPN-детектор: расширить распознавание (✅ сделано — коммит d67371a, релиз v1.4.0)

**Контекст.** На части машин плашка «включите VPN» появляется, хотя VPN
включён. Причина: клиенты типа Clash/V2Ray/Happ работают через системный
прокси или TUN-адаптер с нестандартным именем. Владелец подтвердил:
**системный прокси = VPN включён** (Clash, V2Ray, Happ — все считаются).

На Windows проверка прокси (WinINET `ProxyEnable`) уже есть в
`kdcore/src/VpnMonitor.cpp` — её НЕ трогаем, она работает.

**Что сделать:**

1. `kdcore/src/VpnMonitor.cpp`, `checkOnce()`, список имён адаптеров
   (`kd::containsAny`) — расширить: добавить `"happ", "amnezia", "awg", "clash", "mihomo",
   "sing", "shadowsocks", "v2ray", "xray", "hysteria", "tor", "psiphon",
   "warp", "tailscale", "zerotier", "outline"`. Обратить внимание: `"tun"`
   уже покрывает `tun2socks`; `"sing"` покроет `sing-box`; `"awg"` — Amnezia WireGuard.
2. Добавить третий метод — WinHTTP-дефолт-проки
   (`WinHttpGetDefaultHTTPSecureProxy` или реестр
   `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Internet Settings\Connections`
   `DefaultConnectionSettings`): если WinINET-прокси выключен, а WinHTTP
   задан — считать VPN включённым.
3. Причина решения — в журнал: при смене состояния писать в engine.log
   строку вида `vpn: включён (прокси)` / `vpn: включён (адаптер happ)` /
   `vpn: выключен` (см. mac-реализацию в этом же файле — коммит
   «vpn: три способа детекции» в ветке main).
4. Принцип: сработал хоть один метод → включён. Ошибка проверки ≠ выключен
   (не показывать плашку при сбое проверки).

**Проверка:**

- [ ] TUN-режим Happ/Clash: адаптер опознаётся, плашки нет, лог пишет причину
- [x] Режим системного прокси (без TUN): плашки нет
- [ ] Всё выключено: плашка появляется через ~2 с, лог `vpn: выключен`
- [ ] Автопауза загрузок при пропаже VPN не срабатывает ложно при включённом прокси-VPN
   (следует из того же сигнала состояния, отдельной живой проверки не было)
- [x] `kd_tests.exe` зелёный (45/45); CI `win-build` зелёный (9a56672)

**Итог (03.10).** Список имён адаптеров расширен (happ/amnezia/awg/clash/
mihomo/sing/shadowsocks/v2ray/xray/hysteria/tor/psiphon/warp/tailscale/
zerotier/outline), добавлен третий метод WinHTTP `DefaultConnectionSettings`
(blob[8] & 0x04), причина решения пишется в engine.log
(`vpn: включён (адаптер happ)` / `(прокси)` / `(прокси winhttp)`),
ошибка проверки ≠ выключен. Прокси-режим проверен живьём (ProxyEnable=1 —
плашки нет). TUN-режим Happ и «всё выключено» — у владельца при следующем
сеансе VPN; механика идентична mac-версии и покрыта kd_tests.

## ЗАДАЧА W-2 · Обновление приложения на Windows: обеспечить и принять (✅ сделано — релиз v1.4.0 (коммит 9a56672), живая приёмка 03.10)

**Контекст.** Код автообновления кроссплатформенный (Dарт `UpdateService`
+ `appVersion` из `FLUTTER_VERSION`): проверка `releases/latest` раз в сутки,
плашка «ЕСТЬ ОБНОВЛЕНИЕ X.Y · [ОБНОВИТЬ]», скачивание `.exe` во временную
папку, запуск установщика, закрытие приложения. На mac-версии принято
владельцем (v1.3.0). На Windows живой приёмки ещё не было.

**Что сделать/проверить:**

1. Установлена старая версия (например v1.1.9) → на GitHub публикуется релиз
   новее с ассетом `K-LOAD-VX.Y.Z-Setup.exe` → при запуске приложения
   появляется плашка «ЕСТЬ ОБНОВЛЕНИЕ».
2. Клик «ОБНОВИТЬ» → прогресс скачивания → файл во временной папке (НЕ в
   Загрузках) → Setup.exe запускается → приложение закрывается → установщик

   в installer.iss уже есть).
3. После обновления плашка больше не появляется (версия совпала).
4. Обрыв сети при скачивании → честный тост, приложение живо.
5. Проверить `kd_vpn`-независимость: проверка обновления молчит без сети.

**Важно:** в релизах с mac-only изменениями (v1.3.0) ассета `.exe` нет —
приложение Windows честно молчит. Это норма до первого общего релиза.

## ЗАДАЧА W-5 · Вылет приложения при скачивании YouTube Shorts (→ ожидает Windows, срочно)

**Симптом (репорт владельца).** На Windows при скачивании YouTube Shorts
(`youtube.com/shorts/...`) приложение закрывается во время скачивания.

**Факт с mac-стороны (08.10).** На macOS Shorts качается корректно: probe -J
и скачивание точными аргументами ядра через /shorts/-ссылку проверены живьём
(файл получен, склейка ок). Значит баг платформо-специфичный: Windows-раннер
или kdcore на Windows, а не логика движка.

**Диагностика по порядку:**

1. `%APPDATA%\K LOAD\engine.log` — последние строки перед вылетом: какая
   команда yt-dlp запущена, дошли ли маркеры @T/@F, на каком прогрессе умерло.
2. Журнал событий Windows: Event Viewer → Windows Logs → Application —
   записи Error для kload.exe в момент вылета (код исключения, стек модуль:
   kload.exe / kdcore.dll / flutter_windows.dll).
3. Воспроизведение автотест-хуком (без ручных кликов):
   `$env:KLOAD_AUTOTEST_URL="https://www.youtube.com/shorts/G3BrjbGicbA"; $env:KLOAD_AUTOTEST_GO="1"; <путь>\kload.exe`
4. Прогнать обычное видео (watch?v=...) — если не вылетает, сравнить путь:
   Shorts-ссылки yt-dlp резолвит с редиректом; проверить строку стадии
   «Подключаюсь…»/«Качаю» в момент смерти.

**Гипотезы для проверки:**

- Краш в обработке прогресса/маркеров на Windows-ветке ChildProcess
  (spawnError/код возврата) — см. свежие фиксы spawnError.
- Взаимодействие с новыми механизмами раннера (liveSize/NC-форвардинг):
  событие во время активной загрузки.
- Отсутствие ffmpeg/ffprobe в tools-win рядом с yt-dlp.exe у ПОЛЬЗОВАТЕЛЯ
  (у нас в CI есть; у владельца с Диска — тоже, но проверить у репортёра):
  Shorts часто требуют постскрипт — если ffmpeg не найден, yt-dlp падает
  кодом≠0, а обработка его вывода на Windows может ронять приложение.

**Критерий закрытия:** Shorts качается на живой Windows без вылета (скрин/видео),
kd_tests.exe зелёный, фикс в релизе (следующая версия из pubspec).
